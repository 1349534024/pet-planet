# 宠物星球项目开发协作规范

本文档用于统一四名后端成员和前端成员的项目结构、技术约定、接口风格、数据库规范和联调流程。所有成员开发前先阅读本文档，新增模块、表、接口、消息队列、AI 能力时优先遵守这里的约定。

## 1. 项目目标

宠物星球是一个综合养宠平台，核心业务包含用户体系、宠物档案、宠物商城、订单支付、领养、活体宠物、服务预约、社区、宠物币、商家后台和平台管理后台。

V1.0 优先完成 P0 主链路：

- 注册登录、用户资料、地址、实名认证状态。
- 多宠物档案、成长记录、健康记录、提醒。
- 商品、SKU、购物车、订单、支付、售后、评价。
- 商家入驻基础版、领养信息浏览和申请。
- 社区发布、内容审核、平台管理后台。
- 文件上传、短信、统一鉴权、统一错误码、操作日志。

## 2. 技术栈

### 2.1 后端

- 语言：Python 3.11+
- Web 框架：FastAPI
- ORM：SQLAlchemy 2.x
- 数据库迁移：Alembic
- 业务数据库：MySQL 8.x / PostgreSQL 15+
- 消息队列：RabbitMQ
- AI 编排：LangGraph
- AI 应用框架：LangChain
- 大模型：DeepSeek
- 向量库：Chroma

### 2.2 前端

- 管理后台：Vue 3 + Vite + TypeScript
- 用户端/跨端 App：uni-app
- HTTP 请求：统一封装 request 客户端
- 状态管理：Pinia
- UI 组件库：团队统一后再固定，不允许每个模块自行引入不同组件库

### 2.3 数据库使用原则

项目可以通过 `DATABASE_URL` 切换 MySQL 或 PostgreSQL，但同一个环境只能使用一种业务数据库，禁止成员各自混用。

推荐约定：

- 本地开发：MySQL 或 PostgreSQL 均可，但迁移脚本必须通过团队指定数据库验证。
- 联调/测试环境：统一使用团队指定数据库。
- 生产环境：上线前固定一种，迁移脚本以生产数据库方言为准。

SQLAlchemy 模型应尽量保持方言中立。确实需要数据库专属能力时，必须在 PR 或提交说明中写清楚原因。

## 4. 后端分层规范

后端统一按以下层次开发：

- `api`：FastAPI 路由层，只做参数接收、权限声明、响应返回。
- `schemas`：Pydantic 请求/响应模型。
- `services`：业务逻辑层，负责业务规则、状态流转、事务编排。
- `repositories`：数据库访问层，只负责查询和持久化。
- `models`：SQLAlchemy ORM 模型。
- `core`：配置、安全、错误码、分页、日志、RabbitMQ 等公共能力。
- `tasks`：异步消息生产者和消费者。
- `ai`：LangChain、LangGraph、DeepSeek、Chroma 相关能力。

禁止在路由层直接写复杂 SQL 或业务状态流转。禁止前端直接依赖数据库字段名，所有接口都必须通过 schema 暴露。

## 6. API 统一规范

### 6.1 路径规范

所有接口统一使用版本前缀：

```text
/api/v1/模块名/资源名
```

示例：

```text
GET    /api/v1/pets
POST   /api/v1/pets
GET    /api/v1/pets/{pet_id}
PATCH  /api/v1/pets/{pet_id}
DELETE /api/v1/pets/{pet_id}
```

### 6.2 HTTP 方法

- `GET`：查询。
- `POST`：创建、提交动作。
- `PATCH`：局部修改。
- `PUT`：整体替换，默认少用。
- `DELETE`：删除，业务上优先软删除。

### 6.3 统一响应格式

成功响应：

```json
{
  "code": "SUCCESS",
  "message": "success",
  "data": {}
}
```

分页响应：

```json
{
  "code": "SUCCESS",
  "message": "success",
  "data": {
    "items": [],
    "page": 1,
    "page_size": 20,
    "total": 100
  }
}
```

失败响应：

```json
{
  "code": "AUTH_TOKEN_EXPIRED",
  "message": "登录已过期，请重新登录",
  "data": null
}
```

### 6.4 常用错误码

```text
SUCCESS
VALIDATION_ERROR
UNAUTHORIZED
FORBIDDEN
NOT_FOUND
CONFLICT
RATE_LIMITED
INTERNAL_ERROR

AUTH_INVALID_PHONE
AUTH_INVALID_CODE
AUTH_TOKEN_EXPIRED
AUTH_INVALID_PASSWORD

USER_NOT_FOUND
USER_DISABLED
USER_REAL_NAME_REQUIRED

PET_NOT_FOUND
PET_PERMISSION_DENIED

FILE_INVALID_TYPE
FILE_TOO_LARGE

ORDER_NOT_FOUND
ORDER_STATUS_INVALID
PAYMENT_CALLBACK_INVALID

AUDIT_REQUIRED
AUDIT_REJECTED
```

### 6.5 分页参数

列表接口统一使用：

```text
page: int = 1
page_size: int = 20
```

约束：

- `page >= 1`
- `1 <= page_size <= 100`
- 默认按 `created_at desc` 排序

### 6.6 鉴权规范

用户端接口默认使用：

```http
Authorization: Bearer <access_token>
```

后端提供统一依赖：

- `get_current_user`
- `require_roles`
- `require_permissions`
- `require_real_name`

游客可访问接口必须显式标注，不允许默认放开。

### 6.7 幂等规范

以下接口必须支持幂等：

- 创建订单。
- 支付回调。
- 售后申请。
- 审核决策。
- 宠物币发放/扣减。
- 重要消息发送。

请求头建议：

```http
Idempotency-Key: <uuid>
```

## 7. 数据库设计规范

### 7.1 表命名

- 表名使用小写下划线。
- 表名使用单数或业务明确名称，团队内保持一致。
- 中间表使用 `主表_从表`，例如 `user_role`。

### 7.2 通用字段

业务表默认包含：

```text
id
created_at
updated_at
deleted_at
status
```

高风险或需要审核的表额外包含：

```text
audit_status
audit_reason
audited_by
audited_at
```

### 7.3 金额和积分

- 金额统一使用整数分存储，例如 `price_cent`。
- 宠物币统一使用整数积分存储。
- 不允许使用浮点数存金额。

### 7.4 敏感字段

以下字段必须加密存储或脱敏返回：

- 手机号。
- 身份证号。
- 真实姓名。
- 人脸识别结果。
- 营业执照号。
- 支付相关标识。
- 收款账户。

日志中禁止记录敏感明文。

### 7.5 删除策略

默认使用软删除：

```text
deleted_at is null
```

涉及订单、支付、宠物币、审核、日志的表不允许物理删除。

## 8. Alembic 迁移规范

每个成员新增或修改表结构时必须提交 Alembic 迁移文件。

迁移命名建议：

```text
YYYYMMDD_序号_模块_动作.py
```

示例：

```text
20260706_0001_user_pet_base_tables.py
20260708_0002_order_payment_tables.py
```

要求：

- 一个迁移文件只做一组相关变更。
- `upgrade` 和 `downgrade` 都要可读。
- 不允许直接改已合并迁移文件，必须新增迁移。
- 合并前本地执行迁移到最新版本。

常用命令：

```bash
alembic revision --autogenerate -m "add user pet base tables"
alembic upgrade head
alembic downgrade -1
```

## 9. RabbitMQ 规范

### 9.1 使用场景

以下场景使用 RabbitMQ：

- 短信发送。
- 文件处理、图片审核、视频转码。
- 支付成功后订单后续处理。
- 消息通知。
- 宠物币异步发放。
- 审核任务创建。
- 数据统计事件。
- AI/RAG 异步任务。

### 9.2 Exchange 和 Routing Key

推荐统一使用 topic exchange：

```text
petplanet.events
```

Routing Key 示例：

```text
user.registered
file.uploaded
order.created
order.paid
payment.callback.received
audit.task.created
message.send
petcoin.changed
ai.rag.index.requested
```

### 9.3 消息体规范

```json
{
  "event_id": "uuid",
  "event_type": "order.paid",
  "occurred_at": "2026-07-06T20:00:00+08:00",
  "source": "order-service",
  "data": {},
  "trace_id": "uuid"
}
```

消费者必须处理重复消息，不能假设消息只消费一次。

## 10. AI 能力接入规范

AI 能力不进入 P0 主链路阻塞项，建议作为独立模块逐步接入。

### 10.1 LangChain

用于：

- Prompt 模板管理。
- DeepSeek 调用封装。
- RAG 检索问答。
- 输出解析。

### 10.2 LangGraph

用于需要多步骤状态流转的 AI 任务：

- AI 养宠助手。
- 宠物健康建议。
- 内容安全辅助判断。
- 商家资质材料初审。
- 运营数据分析助手。

### 10.3 DeepSeek

统一封装在后端 `ai` 模块，不允许业务代码直接散落调用模型 API。

建议封装：

- `DeepSeekClient`
- `ChatService`
- `RagService`
- `ModerationAssistService`

### 10.4 Chroma

用于知识库向量检索：

- 新手养宠指南。
- 品种百科。
- 疫苗驱虫知识。
- 服务规则。
- 平台帮助中心。

向量文档必须保留来源字段：

```json
{
  "source": "feeding_guide",
  "title": "幼猫喂养指南",
  "version": "v1",
  "chunk_index": 1
}
```

AI 输出必须提示仅供参考，医疗相关问题必须引导线下就医。

## 17. 五周开发节奏

### 第 1 周

- A：项目基础、登录、用户、角色、宠物档案表。
- B：商品、类目、SKU、购物车基础表。

## 18. A 模块优先落地顺序

因为 A 是公共底座，建议按以下顺序开发：

2. SQLAlchemy Base、Alembic 初始化。
3. 统一响应、错误码、分页。
4. 用户、认证、角色相关表。
5. JWT 登录、刷新、退出。
6. 当前用户和角色权限依赖。
7. 用户资料和地址。
8. 宠物档案 CRUD。
9. 宠物成长记录、健康记录、提醒。

11. 操作日志、敏感信息脱敏。
12. 接口文档和 mock 数据。

## 19. 禁止事项

- 禁止每个人私自定义一套响应格式。
- 禁止接口直接返回 ORM 对象。
- 禁止路由层写复杂业务逻辑。
- 禁止金额使用 float。
- 禁止日志记录手机号、身份证、token 等敏感明文。
- 禁止跳过 Alembic 直接手改数据库。
- 禁止提交 `.env`、密钥、数据库备份。
- 禁止高风险业务绕过审核流。
- 禁止 AI 医疗建议以确定性诊断口吻输出。

1. 确认生产和联调数据库到底使用 MySQL 还是 PostgreSQL。
2. 由 A 先初始化后端工程骨架和公共能力。
3. 四人按本文档分别补充自己模块的表设计和接口文档。
